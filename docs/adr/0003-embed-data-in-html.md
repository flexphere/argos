# ADR 0003: skill が生成する HTML に議論データを埋め込む

- Status: Accepted
- Date: 2026-08-20
- 関連: [ADR 0001](./0001-vite-singlefile-html.md) / [ADR 0002](./0002-bundle-html-in-plugin.md)

## 背景

[ADR 0002](./0002-bundle-html-in-plugin.md) で argos 本体を plugin に同梱し、利用者はビルドせずに単一 HTML を開けるようになった。しかし議論を人に見せるには、依然として **HTML と JSON の 2 つを渡し、受け取った人に Import 操作をさせる**必要がある。

議論グラフは会議ごとの成果物であり、共有されることに意味がある。渡した相手が手順を踏まずに開けるほうがよい。

この案は ADR 0002 で「保留する論点」として記録していたもので、バージョン整合の問題（skill が出した JSON を、どの世代の viewer で開くか）に対する根本解決にもなる。データと viewer が 1 ファイルに固まるため、後から組み合わせを気にする必要が消える。

## 採用案

**skill 実行時に、同梱テンプレート HTML へ抽出結果を焼き込んだ `extractions/<page-id>.html` を生成する。**

- 埋め込み位置は **`</head>` の直前**にある `<script type="application/json" id="argos-embedded-data">`

  当初は「アプリ本体の script より前に置く必要がある」と考えていたが、実測すると `vite-plugin-singlefile` はアプリの script を head の**先頭付近**にインライン化するため、`</head>` 直前は script より後になる。それでも読めるのは、inline の `<script type="module">` が defer 相当で **HTML のパース完了後に評価される**ため。位置は本質的な条件ではない。`</head>` 直前を選んだのは、テンプレートの構造が変わっても安定して見つかる挿入点だからである
- ブラウザは起動時にこの要素を探し、あれば `applyExtraction` + `applyStoredSemantic` を通してグラフを構築する。無ければ従来どおり空グラフで起動する
- **埋め込みデータがある場合、graph store の localStorage 永続化を無効にする**（後述）
- **`extractions/<page-id>.json` は引き続き出力する。** データの正は JSON 側に置き、HTML は配布用の成果物と位置づける。別バージョンの viewer への再 import や、後からの再生成の余地を残すため
- 併せて、ブラウザから **現在の状態を埋め込んだ HTML をダウンロードする Export** を追加する。受け取った HTML を編集して再び HTML として渡せるようにするため

生成は `scripts/embed-fixture.ts` が担い、`build-skill.mjs` で `.claude/skills/argos/scripts/embed-fixture.mjs` に bundle する。既存の `save-fixture` と同じ構成に揃える。

## 埋め込み時に永続化を無効にする理由

graph store は `persist`（localStorage キー `argos-graph`）でグラフを保存している。埋め込み HTML でもこれをそのまま効かせると壊れる。実測した事実は 2 つ。

**1. `file://` でも localStorage は動く。** Import 後にリロードしてもグラフが復元されることを確認した。

**2. 別パスの HTML が同じ localStorage を共有する。** `file://` で開いたページの origin は一律 `file://` になるため、`dist/index.html` で保存した内容が `assets/argos.html` を開いたときにそのまま復元された。**会議ごとに別ファイルとして配った HTML が、互いの状態を奪い合う。**

事実 2 により、「初回だけ埋め込みデータを適用し、以降は編集を保持する」方式は素直には成立しない。会議 A を開いて編集し、次に会議 B を開くと `argos-graph` が B で上書きされ、A に戻ったとき A は「適用済み」なので再適用されず B の内容が表示される。回避するには persist のキーを埋め込みごとに分ける必要があるが、`persist` は `name` を store 生成時に確定させるため、store の初期化構造に手を入れることになる。

そこで**埋め込みがあるときは localStorage に書かない**。配布物が閲覧者のブラウザ状態を汚さず、複数の会議 HTML を開いても干渉しない。編集はセッション中のみ保持され、残したい場合は Export で持ち出す。

判定に必要な要素 ID の定数は `src/schema/embedded.ts` に置き、store / io / skill スクリプトの三者が同じ規約を参照する。`schema` はどの層からも参照でき、依存方向を壊さない。

## 実装上の必須制約: `</script>` の無効化

JSON を `<script>` 要素の中に置く以上、**データ中の文字列が script ブロックを閉じてしまう事故を防がなければならない**。議事録には `<` や `>` が普通に含まれるため、これは理論上の懸念ではない。

`JSON.stringify` の出力に対し、書き出し前に次を置換する。

| 元 | 置換後 | 理由 |
|---|---|---|
| `<` | `<` | `</script>` と `<!--` の両方を無効化する |
| U+2028 | ` ` | JS のパーサが行区切りとして扱う場合がある |
| U+2029 | ` ` | 同上 |

`<` は JSON の文字列エスケープとして valid なので、`JSON.parse` した結果は元の文字列に戻る。デコード側に特別な処理は要らない。

**`</script>` を含む fixture を通す往復テストを必ず置く。** この制約が守られているかを機械的に検証できる状態にしないと、実データで初めて壊れる類の不具合になる。

## 不採用案

### 1. URL のフラグメント / クエリにデータを載せる

`argos.html#<base64>` の形。ファイルが 1 つ増えない利点はあるが、ブラウザや中継サーバの URL 長制限に当たる。実測している fixture でも数 KB あり、実際の会議データはさらに大きい。共有手段が URL に限定されるのも、オフライン配布を重視した ADR 0001 / 0002 の方向と噛み合わない。

### 2. localStorage に事前投入する

投入する手段自体が別の HTML かスクリプトになり、配布物が増える。加えて上述のとおり `file://` の localStorage は全ファイルで共有されるため、会議ごとの分離ができない。

### 2'. 初回のみ適用し、以降は編集を保持する

編集が残るので体験としては自然だが、上述の実測 2 により複数ファイルで破綻する。persist のキーを埋め込みごとに分ければ回避できるものの、store の初期化構造に手を入れる必要があり、得られるものが「リロードで編集が残る」ことに限られる。編集の持ち出しは Export で代替できるため不採用とした。

### 2''. File System Access API で HTML 自身を上書きする

`showSaveFilePicker` は `file://` でも存在し、`isSecureContext` も `true` であることを実測した。しかし**ページが自分自身のファイルハンドルを取得する手段はない**ため、「上書き」といっても利用者が毎回そのファイルを選び直す操作になり、別名保存と変わらない。加えて Firefox / Safari が未対応。同じ目的は Blob + `<a download>` による HTML Export で全ブラウザ向けに達成できるため、そちらを採用した。

### 3. データを base64 の data URI として埋める

script タグに直接置くのと実質同じことをしながら、HTML を開いたときに中身が読めなくなる。デバッグ時に生の JSON が見えるほうがよい。サイズも約 33% 増える。

### 4. 現状維持（HTML と JSON を別々に渡す）

受け取る側に Import 操作を要求し続ける。共有のたびに手順の説明が要るため不採用。ただし **JSON 単体の出力は残す**（採用案参照）ので、この経路が消えるわけではない。

## 結果・影響

**得られるもの**

- 生成された HTML 1 枚を渡すだけで、相手は開くだけで議論グラフを見られる
- データと viewer が同じファイルに固まるため、バージョン整合を考える必要がなくなる

**代償**

- skill の出力が 1 つ増える（`.json` と `.html`）
- HTML のサイズはテンプレート 545KB にデータ分が加算される。fixture が数 KB 程度なら誤差の範囲

**波及**

- `build-skill.mjs` の bundle 対象が 2 本になるため、**CI の鮮度チェックのパス一覧に `embed-fixture.mjs` を追加する**。忘れると ADR 0002 で塞いだ穴を、skill が実行するスクリプトで作り直すことになる
- `io/jsonIO.ts` の `parseImportFile(file)` から `parseImportJson(text)` を切り出す。`parseImportFile` は薄いラッパーとして残すため、`ImportMenu` 側は無改変
- 埋め込みデータの読み出しは DOM に触るため `io/` に置く（`io/imageExport.ts` が DOM を扱う前例がある）。`tests/architecture/dependencies.test.ts` の依存方向は維持される

## 決着した論点

**スキーマ互換方針は規約化しない。**

ADR 0002 から「新しい viewer が古い JSON を常に読めることを規約とするか」を持ち越していたが、本 ADR の採用で **バージョン不一致によって閲覧できなくなる状態が起きなくなった**ため、対応しないことを決定した。

共有される成果物は HTML であり、データと viewer が同じファイルに固まっている。受け取った側は生成時点の argos ごと開くので、後から組み合わせを気にする必要がない。JSON 単体を別バージョンの viewer に読ませる経路は残るが、それは argos を手元に持っている人の操作であり、壊れても再生成できる。

規約を敷いて zod スキーマの変更をオプショナル追加に縛るコストに、現時点で見合わない。将来 JSON 単体の配布が主要な経路になったら、その時点で改めて ADR を起こす。
